High

Crypto-agility Anti-patterns
ID  Common Weakness Enumeration ID  Summary Description
1	cwe321	Hardcoded private key.	A hardcoded private key can be discovered by decompiling. This is a significant vulnerability. Private keys should never be hard coded. They should be kept in key stores.
2	NA	Programmatically editing providers list.	While the JCA API allows applications to change their providers list, it is better practice for the organization to set an organization-preferred provider list in their security .java file and for applications not to override it.
3	NA	Programmatically editing security properties.	Programmatic editing of security properties presents potential for error, misalignment of settings and opens opportunities for bad outcomes. As an example, consider select java security setProperty calls: that is, some properties are particularly relevant to crypto-agility like jdk.tls.disabledAlgorithms, but not package.definition. In addition, it is better style to let the organization set security properties and for individual applications not to override them.
4	NA	Hardcoded provider name.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. An example of this would be hardcoding a JCA Instance call that allows the user to specify which provider they might get an algorithm implementation from. It is better style for the organization to establish preferred provider(s) in a centrally managed security .java file and for individual applications not to override this.
5	NA	Hardcoded key length.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. Also, this makes it easier for discovery. An example of this would be passing in a hardcoded int to the init call of KeyGenerator.
6	NA	Hardcoded protocol choice.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties.
7	NA	Hardcoded algorithm choice.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties.
8	NA	Hardcoded algorithm specific parameters.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. Certain parameters, pertinent to the crafting of the cryptography should not be hardcoded. This is intended for parameters like the encryption exponent for RSA. An example would be initializing a BigInteger with a hardcoded value, then using this to construct an RSAKeyGenParameterSpec.
9	NA	Hardcoded ciphersuite choice.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. An example of this would be hardcoding an array of strings and using setEnabledCipherSuites on an SSLSocket or SSLParameters object.
10	cwe321	Hardcoded certificate.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. An example of this would be hardcoding a .pem certificate as a string in code. A hardcoded certificate can easily be discovered by decompiling, which makes it vulnerable. A better alternative is to keep certificates in a certificate store.
11	NA	Directly setting protocols/ciphersuites on SSL objects.	This is similar to hardcoding in terms of impact, hard to find, change and it makes the source code easy to overlook when updates are needed.
12	NA	Setting SSL context as system default.	It is better to create a custom SSLContext and apply specific settings.
13	cwe321	Hardcoded (symmetric) key.	Hardcoding makes code difficult to maintain and update, which can lead to inadvertent issues and vulnerabilties. A hardcoded key can be discovered by decompiling and thus is vulnerable. It is much better to keep keys in a key store.
14	cwe321	Hardcoded initialization vector.	Block ciphers use initialization vectors and the best practice is that the initialization vector is random and generated anew for each new encryption. A hard coded initialization vector by definition is of course not random and presents a weakness.
15	cwe321	Hardcoded salt.	Since a cryptographic salt is used to augment data (passwords) to lengthen them and randomize them, and protect against multiple entities which happen to have the same password, it needs to be random. Having a hardcoded salt therefore would not provide this protection and greatly increases the danger of attack and discovery of passwords.
